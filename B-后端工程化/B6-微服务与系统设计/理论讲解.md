## 1. 从单体到分布式：你先失去什么

### 1.1 先理解"单体"是什么

**本节概念**：**单体应用（Monolith）**就是把所有功能写在一个程序里、部署在一台机器上（或一个进程里）。就像一个街边小卖部——老板一个人收银、理货、记账全干了。

你之前写的所有 FastAPI 应用，本质上都是单体：

```python
# 一个典型的单体 FastAPI 应用
from fastapi import FastAPI

app = FastAPI()

@app.post("/users")        # 用户模块
def create_user(): ...

@app.post("/orders")       # 订单模块
def create_order(): ...

@app.get("/products")      # 商品模块
def list_products(): ...

# 这三个功能在同一个程序里，部署在同一台机器上
```

单体的好处非常实在：
- **简单**：一个程序启动，全部功能都有了
- **调试方便**：报错信息直接告诉你哪行出了问题
- **事务好办**：下单减库存，两个操作在同一个数据库事务里，要么全成功要么全失败

那为什么还要拆？往下看。

### 1.2 单体什么时候开始"痛"

**本节概念**：当系统大到**一个程序放不下**或**一个团队改不动**时，单体就从一个简单方案变成了瓶颈。具体表现有三类痛。

想象你的小卖部火了，变成全国连锁超市。这时原来的模式出问题了：

**痛点一：改一处要重新部署整个系统**

```python
# 你只改了用户模块的一行代码
@app.post("/users")
def create_user():
    # 改了一行：加了邮箱验证
    ...

# 但整个应用都要重新部署！
# 部署期间，订单、商品、支付全停了
# 就像超市因为要修收银台，把整个超市都关了
```

**痛点二：团队互相踩脚**

10 个开发团队在同一个代码库里改代码。A 团队改了用户表结构，B 团队的订单功能突然就挂了——他们都不知道 A 改了。就像 10 个厨师在同一个灶台上炒菜。

**痛点三：不能按需扩容**

```python
# 双十一时，只有下单功能压力大，用户注册和商品浏览正常
# 但因为是单体，你只能把整个应用复制 10 份
# 每一份都包含用户、订单、商品——即使用户和商品不需要扩容
# 浪费机器资源，也浪费钱
```

### 1.3 拆开之后，你失去了什么

**本节概念**：微服务用"拆"解决了单体痛点，但拆开的同时**失去了单体的便利**——最核心的损失是"确定性"。本节列三个最根本的损失。

**损失一：函数调用变成了网络调用**

```python
# 单体里：下单时查用户信息，一个函数调用
def create_order(user_id):
    user = get_user(user_id)      # 同进程内函数调用，几乎不会失败
    ...

# 微服务里：下单服务和用户服务在不同机器上
def create_order(user_id):
    user = http_get(f"http://user-service/users/{user_id}")  # 网络调用！
    # 这段代码可能因为网络抖动而失败
    # 可能因为用户服务挂了而超时
    # 可能返回了你没预料到的错误格式
    ...
```

**损失二：数据库事务不再简单**

```
单体：一个数据库，一个事务
  BEGIN
  UPDATE 库存 SET count = count - 1 WHERE id = 123
  INSERT INTO 订单 VALUES (...)
  COMMIT  ← 要么全成功，要么全失败

微服务：
  订单服务有自己的数据库
  库存服务有自己的数据库
  你怎么保证"下单 + 减库存"的原子性？
  ← 这就是后面要讲的"分布式事务"问题
```

**损失三：排查问题变成"侦探工作"**

```
单体：报错了 → 看一行日志 → 找到 bug → 修好

微服务：用户说"我的订单没生成"
  → 是网关没转发请求？
  → 是订单服务挂了？
  → 是订单服务调用库存服务超时了？
  → 是库存服务扣成功了但通知订单服务的消息丢了？
  → 是数据库死锁了？
  ← 你需要"链路追踪"（§10）才能在 5 个服务里找到那一跳
```

**一句话总结**：**分布式系统设计的核心不是"高大上"，而是在不可靠的基础设施（网络会断、机器会挂、时钟会偏）上，把业务做得足够可靠。**

## 2. 微服务是什么、不是什么

### 2.1 生活类比：从大卖场到专卖店

**本节概念**：**微服务**是一种**组织软件的方式**——把系统按业务能力拆成多个**可独立部署**的小服务，服务之间通过网络通信。类比：一个大卖场（单体）拆成手机专卖店、服装专卖店、餐饮店（微服务），每家独立运营但共同组成一个商场。

```
大卖场模式（单体）：
  一栋楼里什么都卖——服装、电器、食品、化妆品
  一个经理管所有事

专卖店模式（微服务）：
  手机店、服装店、餐厅各自独立
  每家有自己的店长、自己的收银系统、自己的库存
  顾客通过商场走廊（网络）在店之间走动
```

### 2.2 技术定义

**本节概念**：技术上，一个微服务通常 = **自己的代码仓库 + 自己的数据库 + 独立的部署流水线 + 通过网络 API 对外提供服务**。

```python
# 用户服务（独立部署）
# 仓库：github.com/company/user-service
# 数据库：user_db (PostgreSQL)
@app.get("/users/{id}")
def get_user(id: int):
    return db.query(User).filter(User.id == id).first()

# 订单服务（独立部署）
# 仓库：github.com/company/order-service
# 数据库：order_db (PostgreSQL)
@app.post("/orders")
def create_order(data: OrderRequest):
    # 需要用户信息时，通过网络调用用户服务
    user = requests.get(f"http://user-service/users/{data.user_id}")
    ...
```

### 2.3 微服务不是什么

**本节概念**：三个常见误解——"拆得越细越好"、"新项目就该上微服务"、"微服务比单体快"。逐一澄清。

**误解一："把类拆成多个仓库就叫微服务"**

```python
# 这不是微服务，这是"拆文件"
# 这两个"服务"共享同一个数据库，不能独立部署
# 这叫"分布式单体"——有微服务的复杂，没有微服务的好处
```

**误解二："新项目第一天就该上微服务"**

一个只有 3 个人的创业团队，产品还在验证阶段，拆成 10 个微服务是自杀——你花在运维上的时间会比写业务代码还多。**微服务解决的是"组织规模化"的问题，不是"代码怎么写"的问题。**

**误解三："微服务比单体快"**

一个用户请求在单体里只需要一次函数调用（纳秒级），在微服务里变成一次网络请求（毫秒级）——慢了上千倍。微服务的优势不是单次速度快，而是**能独立扩容瓶颈模块**。

### 2.4 什么时候该拆

**本节概念**：拆的理由应该是业务驱动，不是技术炫技。

| 合理动机 | 例子 |
|---------|------|
| 团队规模大了，不同团队需要独立发布 | 10 个团队改同一个仓库互相阻塞 |
| 某个功能需要独立扩缩容 | 双十一只有下单模块压力大 |
| 技术栈需要异构 | AI 推理模块用 Python，支付模块用 Go |
| 故障隔离 | 一个模块挂了不影响整个系统 |

如果只是为了"赶时髦"，**模块化单体**（代码拆分但部署在一起）是更好的选择。

**模块化单体长这样**：

```python
# 代码按模块拆分，但部署时仍在一起
# 比微服务简单，比大泥球清晰
app/
├── users/          # 用户模块：自己的 models, services, routes
├── orders/         # 订单模块：自己的 models, services, routes
└── products/       # 商品模块：自己的 models, services, routes
```

## 3. 拆分边界：DDD 与有界上下文（直觉版）

### 3.1 拆错了比不拆更痛

**本节概念**：最贵的错误是**拆了两个实际上分不开的服务**——它们互相频繁调用、共享数据库表，最终导致了"分布式单体"：有微服务的所有运维成本，却没有微服务的任何好处。

**生活类比**：把厨房和餐厅拆成两个独立的"公司"。厨师做好一道菜，要打电话通知服务员来取；服务员要问厨师"这个菜还要多久"——本来转个身就能沟通的事，现在变成了跨公司协调。

### 3.2 有界上下文：用"语言边界"找服务边界

**本节概念**：**有界上下文（Bounded Context）**是 DDD（领域驱动设计）里的核心概念。直觉版理解：**同一个词在不同部门里意思不同，这种"意思的不同"就是服务的天然边界。**

举例——一个电商系统里，"用户"这个词在不同人眼里是不同的：

```
客服部门眼里的"用户"：
  - 姓名、手机号、历史投诉、VIP 等级
  - 关心：怎么联系、有没有投诉过

仓储部门眼里的"用户"：
  - 收货地址、默认快递、签收习惯
  - 关心：货送到哪

财务部门眼里的"用户"：
  - 发票抬头、税号、信用额度
  - 关心：能不能开发票、有没有欠款
```

这三个部门的"用户"几乎是三个不同的东西！这就是三个 **有界上下文**：**用户上下文**、**仓储上下文**、**财务上下文**。每个上下文内部用统一的语言，上下文之间通过明确的接口对接。

### 3.3 拆分的三条检查标准

**本节概念**：在画服务边界时，用这三条标准自查。

1. **能用一句话说清这个服务的职责吗？**  
   "用户服务负责管理用户注册、登录和个人信息"——好。  
   "用户服务负责用户相关的东西和部分订单功能"——不好，边界模糊。

2. **能在不访问别的服务数据库的前提下完成核心功能吗？**  
   如果订单服务每次处理订单都必须直接读用户服务的数据库——你拆错了，这两块应该在一起。

3. **团队能独立发布而不必和别的团队协调发布时间吗？**  
   如果每次发布订单服务都要等用户服务先发布——耦合了。

## 4. 同步调用链：超时、重试与幂等

这是微服务里**最常见、最具体、最值得优先搞定**的三个问题。我们用真实代码逐个讲清楚。

### 4.1 超时：别让一个慢服务拖死所有人

**本节概念**：**超时（Timeout）**是说："我等下游服务最多 X 秒，超过这个时间就不等了，直接放弃。"就像你打电话——响 10 声没人接你就挂了，而不是永远拿着电话等。

#### 4.1.1 Why：没有超时会怎样

```python
import requests

# 危险代码：没有超时
def get_user_info(user_id):
    # 如果用户服务挂了，这行代码会永远等下去
    # 默认超时在有些库里是"无限"！
    resp = requests.get(f"http://user-service/users/{user_id}")
    return resp.json()

# 结果：调用这个函数的请求线程被永久占用
# 10 个这样的请求 → 10 个线程卡死 → 整个服务假死
```

**生活类比**：你去银行办事，前面一个人办了两个小时还没完，你后面排了 50 个人全在等。如果银行有"单个业务不超过 15 分钟"的规定（超时），就不会出现这种情况。

#### 4.1.2 What：不只一种超时

| 超时类型 | 含义 | 类比 |
|---------|------|------|
| 连接超时（connect timeout） | 建立 TCP 连接的最长等待时间 | 走到银行门口发现门锁了——立刻知道不开门 |
| 读超时（read timeout） | 连接建立了，等对方返回数据的最长时间 | 进了银行，等了 15 分钟还没办完 |
| 总超时（deadline） | 整个调用的绝对截止时间 | 不管前面几步，11:00 之前必须结束 |

#### 4.1.3 How：正确设置超时

```python
import httpx
import asyncio

async def get_user_info(user_id: str) -> dict:
    """带超时的服务调用"""
    async with httpx.AsyncClient(
        timeout=httpx.Timeout(
            connect=5.0,     # 连接超时 5 秒
            read=10.0,       # 读超时 10 秒
            write=5.0,       # 写超时 5 秒
            pool=5.0,        # 从连接池获取连接的超时
        )
    ) as client:
        resp = await client.get(f"http://user-service/users/{user_id}")
        resp.raise_for_status()  # 如果 HTTP 状态码 >= 400，抛异常
        return resp.json()
```

**超时值怎么设？** 看你的业务 p99 延迟（99% 的请求在多少毫秒内完成），设为 p99 的 2-3 倍。不要拍脑袋。

### 4.2 重试：偶尔的失败不应该让用户看到错误

**本节概念**：**重试（Retry）**是：第一次调用失败了，自动再试几次。但重试有严格的使用条件——**不是所有操作都能重试**。

#### 4.2.1 Why：网络抖动是常态

```
云环境里，网络不是 100% 可靠的
偶发的 TCP 连接断开、DNS 解析失败、负载均衡器切换
这些"抖动"可能只持续几十毫秒
重试一次就成功的概率非常高
```

**生活类比**：你打电话给朋友，第一次占线，过 30 秒再打就通了。你不会因为第一次占线就永远放弃联系。

#### 4.2.2 What：重试的核心原则

**最关键的原则**：只有**幂等**的操作可以安全重试。**幂等**是什么意思？

**本节概念**：**幂等（Idempotent）**：同一个操作执行一次和执行多次，**资源的最终状态是一样的**。

幂等的例子：
- 查询用户信息：查 1 次和查 10 次，用户数据不变 ✓
- 设置用户头像 URL：设 1 次和设 10 次，结果一样 ✓
- 删除指定 ID 的记录：删 1 次成功了，再删第 2 次还是"已删除"状态 ✓

**不幂等**的例子：
- **账户扣款**：扣 1 次是扣 100 元，扣 2 次是扣 200 元 ✗
- **创建订单**：调 1 次生成 1 个订单，调 2 次生成 2 个重复订单 ✗
- **发送短信**：发 1 次和发 10 次完全不同 ✗

#### 4.2.3 How：指数退避 + 抖动

```python
import time
import random
import httpx

def call_with_retry(url: str, max_retries: int = 3):
    """
    带指数退避和抖动的重试。
    
    指数退避：等待时间每次翻倍（1s → 2s → 4s）
    这样给下游恢复的时间越来越长
    
    抖动（jitter）：在上面的基础上加一个随机时间（±25%）
    防止大量客户端恰好在同一时刻一起重试（"惊群效应"）
    """
    last_exception = None
    
    for attempt in range(max_retries + 1):  # +1 是因为第一次不算重试
        try:
            resp = httpx.get(url, timeout=10.0)
            resp.raise_for_status()
            return resp.json()
        except (httpx.TimeoutException, httpx.ConnectError) as e:
            last_exception = e
            if attempt == max_retries:
                break  # 最后一次也失败了，退出循环去抛异常
            
            # 计算等待时间：指数退避 + 抖动
            base_wait = 2 ** attempt  # 0→1, 1→2, 2→4 秒
            jitter = random.uniform(-0.25, 0.25) * base_wait
            wait_time = base_wait + jitter
            
            print(f"第 {attempt + 1} 次失败: {e}，{wait_time:.1f}s 后重试...")
            time.sleep(wait_time)
    
    raise last_exception
```

**对非幂等操作怎么办？用幂等键（Idempotency Key）**：

```python
import uuid

# 调用方：生成唯一 ID，多次重试用同一个 ID
idempotency_key = str(uuid.uuid4())

for attempt in range(3):
    try:
        resp = requests.post(
            "http://order-service/orders",
            json={"product_id": "x", "quantity": 1},
            headers={"Idempotency-Key": idempotency_key}  # 同一个 key！
        )
        break
    except Exception:
        continue

# 服务端：看到相同的 Idempotency-Key 就返回之前的结果，不重复创建
```

```python
# 服务端实现（简化版）
from fastapi import FastAPI, Header, HTTPException
from pydantic import BaseModel

app = FastAPI()
idempotency_store: dict[str, dict] = {}  # 生产环境用 Redis

class CreateOrderRequest(BaseModel):
    product_id: str
    quantity: int

@app.post("/orders")
def create_order(
    req: CreateOrderRequest,
    idempotency_key: str = Header(alias="Idempotency-Key")
):
    # 1. 先检查：这个 key 之前处理过吗？
    if idempotency_key in idempotency_store:
        return idempotency_store[idempotency_key]  # 直接返回之前的结果
    
    # 2. 真正执行业务
    order = do_create_order(req.product_id, req.quantity)
    result = {"order_id": order.id, "status": "created"}
    
    # 3. 把结果存起来，下次同样的 key 直接返回
    idempotency_store[idempotency_key] = result
    
    return result
```

### 4.3 小结：一个够用的"调用下游"模板

```python
import httpx
import uuid
import random
import time

def call_downstream(url: str, method: str = "GET", 
                    body: dict = None, idempotent: bool = False):
    """
    调用下游微服务的通用模板。
    
    参数:
        url: 下游服务的地址
        method: HTTP 方法 (GET/POST/PUT/DELETE)
        body: 请求体（POST/PUT 时用）
        idempotent: 这是不是幂等操作？不是的话我们用幂等键保护
    """
    headers = {}
    if not idempotent and method in ("POST", "PUT", "PATCH"):
        # 对非幂等的写操作，生成幂等键
        headers["Idempotency-Key"] = str(uuid.uuid4())
    
    last_error = None
    
    for attempt in range(4):  # 1 次原始 + 3 次重试
        try:
            resp = httpx.request(
                method, url,
                json=body,
                headers=headers,
                timeout=httpx.Timeout(connect=5.0, read=10.0),
            )
            resp.raise_for_status()
            return resp.json()
        
        except httpx.HTTPStatusError as e:
            # 4xx 错误（客户端错误）一般不重试
            # 重复发送错误的请求也不会变正确
            if 400 <= e.response.status_code < 500:
                raise
            last_error = e
        
        except (httpx.TimeoutException, httpx.ConnectError) as e:
            last_error = e
        
        if attempt < 3:
            wait = (2 ** attempt) + random.uniform(0, 0.5)
            time.sleep(wait)
    
    raise last_error
```

## 5. 熔断与降级

### 5.1 Why：一个挂了的下游能拖死整个系统

**本节概念**：**熔断（Circuit Breaker）**是说：当下游服务连续出错时，调用方先"断开电路"一段时间，不再尝试调用，给下游恢复的时间。就像家里的保险丝——电流过大时自动断开，防止火灾。

**生活类比**：你在手机上点外卖，外卖 App 调用了支付服务。支付服务开始变慢（原本 100ms 现在要 10 秒），但外卖 App 还在不停地发支付请求。结果：

```
外卖 App 有 100 个线程
  ↓ 每个线程都在等支付服务返回（10 秒超时）
  ↓ 100 个线程全被占满
  ↓ 新的"浏览菜单"请求也分配不到线程
  ↓ 整个外卖 App 假死——即使菜单浏览功能根本不需要支付服务
```

这叫**级联故障**（Cascading Failure）。一个服务慢 → 调用它的所有服务都被拖慢 → 整个系统崩溃。

### 5.2 What：熔断器的三种状态

**本节概念**：熔断器是一个状态机，有三种状态。

```
     连续失败 N 次
   ┌──────────────→
关闭(Circuit)         打开(Open)
正常调用             快速失败，不调用
   ←──────────────
     等待 M 秒后
     ↓ "半开"
   半开(Half-Open)
   放一个请求试试
   ├─ 成功 → 回到"关闭"
   └─ 失败 → 回到"打开"
```

**三种状态解释**：

- **关闭（Closed）**：一切正常，请求正常通过。但计数器在记录失败次数。
- **打开（Open）**：失败次数达到阈值，不再尝试调用，直接返回错误。**这叫"快速失败"**——与其等 10 秒超时，不如 1 毫秒就告诉你"现在不行"。
- **半开（Half-Open）**：过了一段时间，放一个请求进去试探。如果成功了，说明下游恢复了，回到"关闭"；如果失败了，说明还没好，回到"打开"。

### 5.3 How：一个教学用的极简熔断器

```python
import time
from enum import Enum

class CircuitState(Enum):
    CLOSED = "closed"          # 正常
    OPEN = "open"             # 熔断
    HALF_OPEN = "half_open"   # 试探

class SimpleCircuitBreaker:
    """
    教学用极简熔断器。
    生产环境请用 tenacity、pybreaker 等成熟库。
    """
    
    def __init__(self, failure_threshold: int = 5, 
                 recovery_timeout: float = 30.0):
        self.failure_threshold = failure_threshold    # 连续失败几次就熔断
        self.recovery_timeout = recovery_timeout      # 熔断后多久尝试恢复
        
        self.state = CircuitState.CLOSED
        self.failure_count = 0
        self.last_failure_time: float = 0.0
    
    def call(self, func, *args, **kwargs):
        """
        包装一个函数调用，自动熔断。
        
        基本用法：
            breaker = SimpleCircuitBreaker()
            result = breaker.call(requests.get, "http://...")
        """
        # 状态一：熔断打开 → 检查是否到了试探时间
        if self.state == CircuitState.OPEN:
            if time.time() - self.last_failure_time >= self.recovery_timeout:
                # 时间到了，进入半开状态，放一个请求试试
                self.state = CircuitState.HALF_OPEN
            else:
                # 时间还没到，快速失败
                raise CircuitBreakerOpenError(
                    f"熔断器开启中，{self.recovery_timeout - (time.time() - self.last_failure_time):.0f}s 后可重试"
                )
        
        # 状态二和状态三：尝试调用
        try:
            result = func(*args, **kwargs)
            # 调用成功 → 重置
            self.state = CircuitState.CLOSED
            self.failure_count = 0
            return result
        except Exception as e:
            self.failure_count += 1
            self.last_failure_time = time.time()
            
            # 失败次数达到阈值 → 打开熔断
            if self.failure_count >= self.failure_threshold:
                self.state = CircuitState.OPEN
            
            raise  # 把原始异常抛给调用方


class CircuitBreakerOpenError(Exception):
    """熔断器开启时抛出的异常"""
    pass


# 使用示例
breaker = SimpleCircuitBreaker(failure_threshold=3, recovery_timeout=10)

def call_inventory_service(item_id):
    return breaker.call(
        httpx.get,
        f"http://inventory-service/items/{item_id}",
        timeout=httpx.Timeout(5.0)
    )
```

### 5.4 降级：保不住完美就保个"还行"

**本节概念**：**降级（Degradation）**是：当某个功能不可用时，不返回错误，而是返回一个"打了折扣但还能用"的结果。

**生活类比**：你点外卖时，App 首页有个"猜你喜欢"模块。如果推荐算法服务挂了，App 不会显示"错误"——它直接展示一个默认的热门榜单。你依然可以点餐。这就是降级。

```python
def get_recommendations(user_id: str) -> list[dict]:
    """获取推荐商品，失败时降级到热门榜单"""
    try:
        resp = httpx.get(
            f"http://recommendation-service/users/{user_id}/recommendations",
            timeout=httpx.Timeout(connect=2.0, read=3.0),
        )
        return resp.json()
    except (httpx.TimeoutException, httpx.ConnectError):
        # 推荐服务挂了 → 降级：返回热门商品
        print("推荐服务不可用，降级到热门榜单")
        return get_hot_items(limit=10)

def get_hot_items(limit: int) -> list[dict]:
    """热门榜单——不需要推荐算法，直接查数据库"""
    # 在 Redis 里缓存了一份，每日更新
    return redis.lrange("hot_items", 0, limit - 1)
```

**降级 vs 熔断的区分**：
- 熔断是**调用方主动断开**，保护自己
- 降级是**服务方或调用方提供备选方案**，保护用户体验

## 6. 限流与背压

### 6.1 Why：没有限流的系统等于没有刹车

**本节概念**：**限流（Rate Limiting）**控制"每秒最多处理多少请求"。没有限流，突发流量会直接打垮服务——数据库连接池耗尽、内存溢出、进程崩溃。

**生活类比**：地铁站入口的限流护栏——不是不让你进，而是"每秒钟最多通过 N 人"。没有这个机制，早高峰所有人一起冲进去，站台会出踩踏事故。

### 6.2 四种限流算法（直觉 + 代码）

#### 6.2.1 固定窗口计数器

**本节概念**：把时间切成固定大小的窗口（如 1 秒），每个窗口内计数，超过上限就拒绝。**简单但有边界问题。**

```python
import time

class FixedWindowRateLimiter:
    """
    固定窗口限流器。
    缺点：窗口边界处可能"双倍放行"。
    比如限制每秒 10 个请求，0.9s-1.0s 来了 10 个，1.0s-1.1s 又来了 10 个，
    在 0.9s-1.1s 这个实际 0.2 秒的时间段里放了 20 个请求——超过了限制。
    """
    
    def __init__(self, max_requests: int, window_seconds: float):
        self.max_requests = max_requests
        self.window_seconds = window_seconds
        self.window_start = time.monotonic()
        self.counter = 0
    
    def allow(self) -> bool:
        now = time.monotonic()
        # 是否进入下一个窗口？
        if now - self.window_start >= self.window_seconds:
            self.window_start = now
            self.counter = 0
        
        if self.counter < self.max_requests:
            self.counter += 1
            return True
        return False
```

#### 6.2.2 滑动窗口（更平滑）

**本节概念**：不是看"当前这个固定的 1 秒窗口"，而是看"过去 1 秒内"——用更细的 bucket 来近似滑动。更准确，但实现稍复杂。

```python
import time
from collections import deque

class SlidingWindowRateLimiter:
    """
    滑动窗口限流器——用时间戳队列实现。
    记录每个请求的时间，扔掉窗口外的旧记录。
    """
    
    def __init__(self, max_requests: int, window_seconds: float):
        self.max_requests = max_requests
        self.window_seconds = window_seconds
        self.timestamps: deque[float] = deque()
    
    def allow(self) -> bool:
        now = time.monotonic()
        # 扔掉窗口外的旧时间戳
        while self.timestamps and now - self.timestamps[0] > self.window_seconds:
            self.timestamps.popleft()
        
        if len(self.timestamps) < self.max_requests:
            self.timestamps.append(now)
            return True
        return False
```

#### 6.2.3 令牌桶（最常用）

**本节概念**：想象一个桶，以固定速率往里面放令牌。每个请求来的时候要从桶里取一个令牌，取到了就放行；桶空了就拒绝。桶有容量上限——允许一定的"突发"但限制平均值。

```python
import time

class TokenBucketRateLimiter:
    """
    令牌桶限流器。
    
    参数:
        rate: 每秒放入多少个令牌（平均速率）
        capacity: 桶最多能装多少个令牌（允许的突发量）
    
    比如 rate=10, capacity=20：
    - 平均每秒 10 个请求
    - 但可以短时间突发到 20 个（只要桶里有库存）
    """
    
    def __init__(self, rate: float, capacity: int):
        self.rate = rate
        self.capacity = capacity
        self.tokens = float(capacity)   # 当前令牌数，初始满的
        self.last_refill = time.monotonic()
    
    def allow(self, tokens_needed: int = 1) -> bool:
        # 1. 先补充：按时间差计算新令牌
        now = time.monotonic()
        elapsed = now - self.last_refill
        self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
        self.last_refill = now
        
        # 2. 检查令牌够不够
        if self.tokens >= tokens_needed:
            self.tokens -= tokens_needed
            return True
        return False
```

#### 6.2.4 算法对比

| 算法 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 固定窗口 | 实现简单 | 边界突刺 | 不严格的限流 |
| 滑动窗口 | 平滑精确 | 内存占用稍大 | API 限流 |
| 令牌桶 | 允许突发，平均值可控 | 需要调 rate/capacity | **推荐，最常用** |
| 漏桶 | 恒定输出速率 | 不允许突发 | 流量整形 |

### 6.3 背压：跟不上就说"慢点"

**本节概念**：**背压（Backpressure）**：当下游处理不过来时，主动告诉上游"慢一点"。就像自助餐厅里，厨师看到取餐区快空了，告诉服务员"先别带新客人进来"。

```python
# 背压的三种常见实现方式

# 方式一：有界队列 + 拒绝
from asyncio import Queue

async def worker(queue: Queue):
    while True:
        item = await queue.get()
        await process(item)

# 生产者
try:
    queue.put_nowait(task)   # 队列满了会抛异常 → 上游就知道要慢下来
except asyncio.QueueFull:
    # 返回 503 Service Unavailable，告诉调用方稍后重试
    raise HTTPException(status_code=503, detail="服务繁忙，请稍后重试")

# 方式二：HTTP 429 Too Many Requests + Retry-After 头
# 方式三：TCP 层背压——接收窗口满了就不 ACK
```

## 7. API 网关与服务发现（直觉）

### 7.1 API 网关：给所有微服务装一个"前台"

**本节概念**：**API 网关（API Gateway）**是所有请求的**统一入口**。客户端只需要知道网关的地址，不需要知道后面有多少个微服务、它们各自在哪个 IP 上。

**生活类比**：酒店前台。你打电话到酒店，只需要知道酒店的总机号码（网关），说出你要找的人（路由），前台帮你转接到对应的房间（微服务）。你不需要知道那个房间的内线号码。

```
没有网关时（客户端直接调多个服务）：
  手机 App → 用户服务 (192.168.1.10:8000)
  手机 App → 订单服务 (192.168.1.11:8001)
  手机 App → 商品服务 (192.168.1.12:8002)
  ← App 要知道 3 个地址！而且地址变了 App 也要改

有网关时：
  手机 App → https://api.myapp.com (网关)
    → 网关看 URL: /users/* → 转发到用户服务
    → 网关看 URL: /orders/* → 转发到订单服务
    → 网关看 URL: /products/* → 转发到商品服务
  ← App 只知道一个地址！
```

**网关通常还做什么**：

| 功能 | 说明 |
|------|------|
| 路由 | `/users/*` → 用户服务，`/orders/*` → 订单服务 |
| 认证 | 在网关层检查 JWT Token，通过后转发，不用每个服务自己做 |
| 限流 | 在入口处统一限流，防止个别用户滥用 |
| 日志/监控 | 每个请求经过网关时记一笔，统计 QPS 和延迟 |
| TLS 终结 | 在网关处解密 HTTPS，内部用 HTTP（内网相对安全） |
| 请求聚合 | 一个页面需要多个服务的数据？网关帮你一起调 |

### 7.2 服务发现：机器 IP 会变，怎么办

**本节概念**：**服务发现（Service Discovery）**解决"我该往哪个 IP 发请求"的问题——服务的实例数量、IP 地址会动态变化（扩容、缩容、重启），不能让调用方把这些信息写死在代码或配置文件里。

**生活类比**：114 查号台。你不会在家里存一本全城所有餐厅的电话号码（而且餐厅会换号码、倒闭、新开），你只需要打 114，告诉接线员"帮我查最近的肯德基"，接线员从最新的数据库里找给你。

```python
# 没有服务发现时（坏的做法）
USER_SERVICE_URL = "http://192.168.1.10:8000"  # 写死 IP！
ORDER_SERVICE_URL = "http://192.168.1.11:8001" # 换一台机器就要改代码

# 有服务发现时（好的做法）
# 方式一：DNS（K8s 内置）
USER_SERVICE_URL = "http://user-service"        # 用域名，DNS 解析到当前健康实例
ORDER_SERVICE_URL = "http://order-service"

# 方式二：注册中心（Consul/Eureka/Etcd）
# 服务启动时向注册中心"报到"
# 调用方先问注册中心"有哪些可用的用户服务实例"
instances = consul.get_healthy_instances("user-service")
# → [("192.168.1.10", 8000), ("192.168.1.11", 8000)]
chosen = random.choice(instances)  # 随机选一个健康的
```

## 8. CAP 与一致性：别被名词吓到

### 8.1 生活入题：银行转账的烦恼

**本节概念**：**CAP 定理**说：在网络分区（P）发生时，你只能在**一致性（C）**和**可用性（A）**之间二选一。不是日常可以"都要"，而是**故障时必须做出取舍**。

你转 100 块钱给朋友：
1. 你的账户扣 100
2. 朋友的账户加 100

如果步骤 1 成功、步骤 2 之前银行系统网络断了——怎么办？

- **方案 A（保一致性 C）**：把步骤 1 也撤销（回滚），你俩的账户都没变化。但在这期间，你的账户被锁住不能用——**牺牲了可用性**。
- **方案 B（保可用性 A）**：你的钱先扣了，朋友的账户等网络恢复再加。两边都能正常使用——但短时间内数据不一致（你少钱了，朋友没多钱）。

这就是 CAP 的直觉：**网络出问题时，你要么选"任何时刻数据都是对的（C）"，要么选"任何时候系统都能用（A）"**。没有两全其美。

### 8.2 一致性光谱：不只是"一致"和"不一致"

**本节概念**：一致性有很多级别，从最严格的到最宽松的。不同业务选不同级别——不是非黑即白。

```
强一致性 ←————————————————————————————→ 最终一致性
(你刚写完，任何人读到的一定是最新的)      (过一段时间后，大家看到的一样)

线性一致性    顺序一致性    因果一致性    最终一致性
(最强，最贵)  (大多数场景够)              (最弱，最便宜)
```

| 级别 | 含义 | 例子 |
|------|------|------|
| 强一致（线性化） | 任何时刻，任何人看到的数据都一样 | 银行账户余额 |
| 最终一致 | 没人更新后，最终大家看到的一样 | 微博粉丝数（差几个没关系） |
| 因果一致 | 有因果关系的操作有序，无关的可以乱 | 微信朋友圈：看到评论前一定先看到原文 |

**怎么选？** 问自己：**"如果用户看到的是 1 秒前的旧数据，会出事吗？"**  
- 会出事（钱算错）→ 强一致，用 PostgreSQL 单库
- 不会出事（微博点赞数差几个）→ 最终一致，用缓存 + 异步同步

## 9. 分布式事务与 Saga

### 9.1 Why：跨服务的事务没有"银弹"

**本节概念**：在单体里，数据库自带的事务（BEGIN/COMMIT/ROLLBACK）搞定一切。在微服务里，一个业务操作可能跨越多个服务和多个数据库——没有哪个数据库能管到另一个数据库的事务。

**生活类比**：你计划了一个旅行：
1. 订机票 ✈️
2. 订酒店 🏨
3. 租车 🚗

如果用单体"事务"的方式，你得同时打电话给三个公司，三家公司同时说"订好了"——这不可能。现实中的做法是：依次操作，如果某一步失败了，把前面成功的取消掉。

### 9.2 Saga：拆成多步，每步可撤销

**本节概念**：**Saga** 把一个大事务拆成多个**本地事务**（每个在自己的数据库里完成），每个本地事务有一个对应的**补偿操作**（撤销/冲正）。如果某一步失败了，按**逆序**执行补偿。

```
下单 Saga（正常流程）：
  Step 1: 订单服务 → 创建订单（状态=待支付） 
  Step 2: 库存服务 → 锁定库存
  Step 3: 支付服务 → 扣款
  Step 4: 订单服务 → 更新订单（状态=已支付）

下单 Saga（补偿流程——假设 Step 3 支付失败）：
  Step 3 失败 → 
    补偿 Step 2: 库存服务 → 释放库存（解锁）
    补偿 Step 1: 订单服务 → 更新订单（状态=已取消）
```

```python
# Saga 的简化 Python 实现
class OrderSaga:
    async def execute(self, order: OrderRequest):
        """执行下单 Saga"""
        order_id = None
        inventory_locked = False
        
        try:
            # Step 1: 创建订单
            order_id = await self.order_service.create(order)
            
            # Step 2: 锁定库存
            await self.inventory_service.lock(order.product_id, order.quantity)
            inventory_locked = True
            
            # Step 3: 扣款
            await self.payment_service.charge(order.user_id, order.amount)
            
            # 全部成功
            await self.order_service.update_status(order_id, "paid")
            
        except Exception as e:
            # 开始补偿（逆序撤销）
            if inventory_locked:
                await self.inventory_service.unlock(order.product_id, order.quantity)
            if order_id:
                await self.order_service.update_status(order_id, "cancelled")
            raise

# 对比：单体里的写法
def create_order_monolith(order):
    with db.transaction():  # 一个事务搞定，简单！
        db.execute("INSERT INTO orders ...")
        db.execute("UPDATE inventory SET count = count - 1 ...")
```

**更可靠的 Saga 实现——发件箱模式（Outbox Pattern）**：

**本节概念**：发件箱确保"写数据库"和"发消息"是一个原子操作——把要发的消息和业务数据写在同一个数据库事务里，由一个后台进程扫描并投递。

```python
# 发件箱模式：保证"业务变更"和"通知下游"的原子性
def create_order(order_data):
    with db.transaction():
        # 1. 业务操作
        order = db.insert("orders", order_data)
        
        # 2. 在同一个事务里，把要发的消息写入 outbox 表
        db.insert("outbox", {
            "event_type": "order.created",
            "payload": json.dumps({"order_id": order.id}),
            "status": "pending"
        })
    # 事务提交 → 两个 INSERT 要么一起成功，要么一起失败
    
    # 一个后台进程（独立于这个请求）扫描 outbox 表，
    # 把 pending 的消息发到消息队列，成功后再标记为 sent
```

## 10. 可观测性三件套：日志、指标、链路追踪

### 10.1 为什么需要这三样东西

**本节概念**：单体时，出了问题看一个日志文件就差不多了。微服务时代，一个请求可能经过 5 个服务——你需要**日志**看每个服务说了什么、**指标**看整体健康趋势、**链路追踪**看一个请求的完整路径。

**生活类比**：快递系统。

- **日志** = 每个中转站的扫描记录（快件 X 于 10:23 到达北京分拣中心）
- **指标** = 仪表盘（今天处理了 10 万件，平均耗时 2.3 小时，错误率 0.1%）
- **链路追踪** = 一个快递的完整轨迹（深圳→广州→北京→配送员李师傅→已签收）

### 10.2 日志：结构化，带 trace_id

```python
import logging
import uuid
import json
from datetime import datetime, timezone

# 不好的日志：人眼能读，但机器解析不了
print(f"订单 {order_id} 创建成功")

# 好的日志：结构化 JSON，机器可读
logger = logging.getLogger(__name__)

def create_order(order_data):
    trace_id = str(uuid.uuid4())  # 贯穿整个请求链路的唯一 ID
    
    logger.info(json.dumps({
        "event": "order.created",
        "order_id": order_data["id"],
        "trace_id": trace_id,
        "timestamp": datetime.now(timezone.utc).isoformat(),
    }))
    
    # 调用下游时，把 trace_id 传过去（通常放在 HTTP 头里）
    ...
```

### 10.3 指标：QPS、延迟分位数、错误率

**本节概念**：指标不是单次的，而是**聚合的**。最关键的四个信号（Google SRE 称为"四个黄金信号"）：

| 指标 | 含义 | 为什么重要 |
|------|------|-----------|
| **延迟（Latency）** | 请求花了多长时间？ | 用 p50/p90/p99，不要只看平均值 |
| **流量（Traffic）** | 每秒多少请求（QPS）？ | 突发流量是故障的先兆 |
| **错误率（Errors）** | 多少请求失败了（5xx/超时）？ | 最直接的故障信号 |
| **饱和度（Saturation）** | 系统有多"满"（CPU/内存/连接池）？ | 预测什么时候需要扩容 |

**为什么不用平均值？** 1% 的用户每次等 10 秒，剩下 99% 等 10 毫秒——平均值 110 毫秒，看起来"不错"。但那 1% 的用户体验极差。**用分位数：p50、p90、p99。**

```
p50（中位数）= 50% 的请求比这个值快
p90 = 90% 的请求比这个值快（10% 的用户体验比这个差）
p99 = 99% 的请求比这个值快（1% 的用户体验比这个差）
```

### 10.4 链路追踪：一个请求的"旅行日记"

**本节概念**：链路追踪（Distributed Tracing）记录一个请求从进入系统到返回响应的完整路径，包括经过的每个服务和每次调用的耗时。

```
用户请求 /api/orders (trace_id: abc123)
│
├─ 网关 (2ms)
│  └─ 认证检查 (1ms)
│
├─ 订单服务 (45ms)
│  ├─ 查询用户信息 (20ms) ← 调用用户服务
│  ├─ 查询库存 (15ms)     ← 调用库存服务
│  └─ 写数据库 (10ms)
│
└─ 总耗时: 47ms

有了这张图，你一眼就能看出"哪个环节慢"。
```

## 11. 容器化与 K8s 入门直觉

### 11.1 容器：让"在我机器上能跑"不再是个笑话

**本节概念**：**容器（Container）**把应用程序和它需要的所有依赖（Python 版本、系统库、环境变量）打包在一起，像一个"自带厨房的餐车"——不管开到哪，做出来的菜都一样。

**Dockerfile 示例**：

```dockerfile
# Dockerfile：定义容器的"配方"
FROM python:3.11-slim          # 基于 Python 3.11 官方镜像

WORKDIR /app                   # 容器里的工作目录
COPY requirements.txt .
RUN pip install -r requirements.txt  # 安装依赖

COPY . .                       # 把代码复制进去

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
# 容器启动时自动执行这个命令
```

### 11.2 K8s：给容器们配一个"调度中心"

**本节概念**：**Kubernetes（K8s）**是容器编排平台——你告诉它"我要运行 3 个订单服务、2 个用户服务、1 个 Redis"，它就自动帮你调度到空闲机器上、监控健康、挂了自动重启、流量高了自动扩容。

K8s 最核心的概念（先记住这四个）：

| 概念 | 一句话 |
|------|------|
| **Pod** | 最小的调度单位，一个 Pod 里通常跑一个容器（你的 FastAPI 应用） |
| **Service** | 给一组 Pod 提供稳定的访问地址（服务发现靠它） |
| **Deployment** | 声明"我要 3 个副本，用这个镜像"，K8s 保证实际状态=期望状态 |
| **Ingress** | 类似 API 网关，把外部 HTTP 流量路由到 Service |

## 12. 与 AI Agent 后端的关系

**本节概念**：本章学的每个可靠性模式，在 AI Agent 后端里都有直接对应的应用场景。

| 微服务模式 | AI Agent 后端场景 |
|-----------|-----------------|
| **超时** | 调用 LLM API（OpenAI/Claude）可能 30 秒才生成完，必须有合理超时 |
| **重试 + 幂等** | LLM API 的 429（限流）和 5xx 需要重试；工具调用幂等（如发邮件不能重发） |
| **熔断** | LLM 连续返回错误 → 熔断，快速失败，不要卡死用户请求 |
| **降级** | 大模型不可用时，切到小模型或返回缓存结果（本地模型兜底） |
| **限流** | OpenAI API 有 rate limit，客户端的限流器能避免被 429 封号 |
| **Saga / Outbox** | Agent 长任务：写数据库 + 发 MQ → 用 Outbox 保证不丢消息 |
| **SSE + 网关超时** | 流式输出（ChatGPT 打字机效果）要经过网关和超时配置 |
| **链路追踪** | 一个 Agent 请求 → LLM → 工具 A → 工具 B → 返回，trace_id 贯穿全程 |

**具体代码模式**：

```python
# Agent 后端里典型的"调用 LLM + 重试 + 熔断"组合
import asyncio
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=1, max=10),
    retry=retry_if_exception_type((httpx.TimeoutException, httpx.HTTPStatusError))
)
async def call_llm_with_retry(messages: list[dict]) -> str:
    """
    调用 LLM，自动重试 3 次，指数退避。
    配合 §4 的超时和 §5 的熔断，就是生产级 Agent 的标配。
    """
    async with httpx.AsyncClient(timeout=30.0) as client:
        resp = await client.post(
            "https://api.openai.com/v1/chat/completions",
            headers={"Authorization": f"Bearer {api_key}"},
            json={"model": "gpt-4", "messages": messages},
        )
        resp.raise_for_status()
        return resp.json()["choices"][0]["message"]["content"]
```

## 14. 常见误区

**本节概念**：以下是微服务面试和实际工作中最容易犯的判断错误。

### 误区 1："微服务 = 架构升级，单体 = 落后"
**纠正**：微服务和单体是两种不同的工程取舍，不是先进 vs 落后。Netflix、Amazon 用微服务，但很多赚钱的 SaaS 公司就是单体。**选择取决于团队规模、业务阶段和运维能力。**

### 误区 2："CAP 定理 = 三选二，所以总能选两个"
**纠正**：CAP 是**网络分区（P）发生时**的取舍——分区是外部条件，不是你能选的。日常网络正常时，C 和 A 可以兼得。真正的问题是：**"分区发生时，你选 C 还是 A？"**

### 误区 3："用了 Kubernetes 就是微服务了"
**纠正**：K8s 是容器编排工具，可以管单体、可以管微服务。把单体容器化部署到 K8s 上 ≠ 微服务。

### 误区 4："QPS 上不去？再拆几个微服务就好了"
**纠正**：拆微服务通常会让单次请求变慢（多了网络调用）。扩容瓶颈模块才是正解。拆之前先查：能不能加缓存？能不能加索引？能不能用异步？

### 误区 5："熔断、重试、超时——这些是纯后端知识，Agent 不用管"
**纠正**：Agent 调用 LLM API 和工具也是网络调用，同样面临超时、失败、限流。甚至更需要——因为 Agent 可能一次任务调 5 个工具，任何一环失败都可能让整个任务前功尽弃。

## 15. 面试考点

### 15.1 微服务优缺点

**问：什么时候用微服务，什么时候用单体？**  
**答**：团队 5 人以下、产品还在验证阶段 → 模块化单体。团队 20 人以上、不同模块有独立发布和扩容需求 → 微服务。核心判断标准是**组织的沟通成本**和**独立的伸缩需求**，不是技术炫技。

### 15.2 超时、重试、幂等

**问：HTTP 哪些方法是幂等的？**  
**答**：GET、HEAD、PUT、DELETE 是幂等的（按 HTTP 协议定义）。POST 不是幂等的——多次 POST 可能创建多个资源。PATCH 不保证幂等。

**问：重试只对哪些操作安全？**  
**答**：只对幂等操作安全。对于非幂等操作（如创建订单、扣款），必须配合幂等键使用。

### 15.3 熔断 vs 降级

**问：熔断和降级的区别？**  
**答**：熔断是调用方主动快速失败，保护自己不被慢下游拖死。降级是提供备选方案（缓存、默认值、简化功能），保护用户体验。熔断关注"不调了"，降级关注"调不通时返回什么"。

### 15.4 CAP 直觉

**问：CAP 定理是什么？用简单的话解释。**  
**答**：当分布式系统的网络出现故障（分区）时，你必须在"保持数据一致"和"保持系统可用"之间做出选择。银行转账选一致性（宁可暂时不可用也不能算错账），社交媒体选可用性（微博点赞数差几个没关系，但不能刷不出来）。

### 15.5 限流算法

**问：常用的限流算法有哪些？**  
**答**：固定窗口（简单但边界突刺）、滑动窗口（更平滑）、令牌桶（允许突发，最常用）、漏桶（恒定输出速率）。生产环境推荐令牌桶。

### 15.6 Saga 与分布式事务

**问：微服务间怎么做"事务"？**  
**答**：没有真正的跨服务数据库事务。用 Saga 模式：把大操作拆成多个本地事务，每个有对应的补偿操作。某步失败时，逆序执行已成功步骤的补偿。更可靠的做法是配合发件箱模式，确保每一步的通知不丢失。
