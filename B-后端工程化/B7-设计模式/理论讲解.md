## 1. 怎么学模式才不算白学

### 1.1 设计模式到底解决什么问题

**本节概念**：**设计模式**是前人在面向对象编程中反复遇到的**通用问题及其可复用解法**。它不是银弹，而是一套被验证过的"代码组织方式"，让程序在面对变化时更容易改。

**生活类比**：造房子有标准户型图——两室一厅、三室两厅。每种户型解决了特定的居住问题（一家三口、三代同堂）。你不需要自己从零发明户型，可以直接参考这些"模式"，根据实际情况调整。设计模式之于代码，就像户型图之于房子。

### 1.2 学模式的正确姿势

**本节概念**：不要背名字、不要记类图。按这个顺序：**先认痛（我代码哪不舒服）→ 找到对应的模式（哦，原来这个问题有标准解法）→ 写代码验证**。

```
错的学法：背"单例模式是确保一个类只有一个实例" → 不知道什么时候用 → 面试说完就忘

对的学法：
  1. "我的代码全局配置散落在各处，改了这里忘了那里" → 这是个"集中管理"的痛
  2. "原来可以用单例 + 配置对象解决" → 找到了模式
  3. 写出来，看看依赖关系是不是变清晰了 → 验证
```

### 1.3 GoF 23 是什么

**本节概念**：**GoF（Gang of Four，四人帮）**是指 1994 年出版的《设计模式：可复用面向对象软件的基础》一书及其 23 种模式。这些模式分为三类：**创建型**（怎么产对象）、**结构型**（类和对象怎么组合）、**行为型**（对象间怎么协作）。

**这些模式过时了吗？** 没有。但应用方式变了——很多模式已经被现代语言的语法（如 Python 装饰器、迭代器）内建了，但思想（解耦、开闭原则）没变。

## 2. GoF 23：整合速览

**本节概念**：本节约 23 种经典模式，按常见痛点归类 + 一句话速查。不逐条长篇大论，重点去 §3-§10 深入讲最常用的几种。

### 2.1 按痛点归类

| 你在痛什么 | 常提到的模式 |
|------------|-------------|
| 规则/算法经常换、不想到处改 if-else | **策略**、**状态**；流程固定只变某几步用**模板方法** |
| 树形结构、要统一对待"单个 vs 组合" | **组合**；在稳定结构上叠加遍历/报表操作 → **访问者** |
| 第三方/老接口跟我不一致 | **适配器**；子系统太杂想一口对外 → **外观** |
| 两个独立维度组合爆炸 | **桥接** |
| 运行时给对象"加料"又不改原类 | **装饰器**；要控制访问、打日志替身 → **代理** |
| 一个变、好多对象都要跟着动 | **观察者**；对象互相指来指去 → **中介者** |
| 多个处理者依次试、不想写长 if-else | **责任链** |
| 操作要排队、撤销、日志 | **命令** |
| 构造复杂、参数多、步骤多 | **建造者**；子类决定具体类型 → **工厂方法**；整套产品族 → **抽象工厂**；复制比新建便宜 → **原型**；全局唯一入口 → **单例** |
| 遍历方式要统一、又不想暴露内部 | **迭代器** |
| 要快照/回滚对象状态 | **备忘录** |
| 海量小对象内存吃不消 | **享元** |
| 小语言/规则引擎 | **解释器**（日常业务少见） |

### 2.2 二十三式一句话速查

| # | 模式 | 一句话 | 类型 |
|---|------|--------|------|
| 1 | **单例** | 全局只要一个实例（注意测试与并发） | 创建型 |
| 2 | **工厂方法** | 父类定接口，子类决定实例化哪个具体类 | 创建型 |
| 3 | **抽象工厂** | 一次创建一整套配套产品，避免风格混用 | 创建型 |
| 4 | **建造者** | 分步构造复杂对象，治构造参数爆炸 | 创建型 |
| 5 | **原型** | 用克隆代替昂贵构造 | 创建型 |
| 6 | **适配器** | 包一层，让不兼容接口能对接 | 结构型 |
| 7 | **桥接** | 抽象与实现解耦，治多维度类爆炸 | 结构型 |
| 8 | **组合** | 树结构里叶子和容器同一套操作 | 结构型 |
| 9 | **装饰器** | 动态叠职责，少子类（与 Python `@` 语法同名不同义） | 结构型 |
| 10 | **外观** | 给复杂子系统一个简单门面 | 结构型 |
| 11 | **享元** | 共享不变部分，省内存 | 结构型 |
| 12 | **代理** | 替身控制访问（懒加载、保护、日志等） | 结构型 |
| 13 | **责任链** | 请求沿链传递，直到有人处理 | 行为型 |
| 14 | **命令** | 把请求变对象，支持撤销、队列、日志 | 行为型 |
| 15 | **解释器** | 为小型语法建解释执行结构 | 行为型 |
| 16 | **迭代器** | 统一遍历，不暴露内部表示 | 行为型 |
| 17 | **中介者** | 多对象不直连，改通过中介，降耦合 | 行为型 |
| 18 | **备忘录** | 外部存快照，支持恢复 | 行为型 |
| 19 | **观察者** | 一主题多订阅，状态变则通知 | 行为型 |
| 20 | **状态** | 状态一变行为就变，整理状态机 | 行为型 |
| 21 | **策略** | 封装算法族，可互换 | 行为型 |
| 22 | **模板方法** | 骨架固定，子类填步骤 | 行为型 |
| 23 | **访问者** | 数据结构稳定，往上面挂新操作 | 行为型 |

### 2.3 学这些是在对抗什么（三个永恒问题）

1. **改一处要改十处** → 靠**解耦**（策略、观察者、中介者）
2. **加新功能要翻遍旧代码** → 靠**开闭原则**（装饰器、策略）
3. **逻辑粘死在某个调用链里，换不了** → 靠**依赖倒置**（工厂、适配器）

## 3. 策略模式——规则经常变怎么办

### 3.1 Why：没有策略模式时

**本节概念**：当业务规则有多种算法，且需要根据场景切换时，新手最容易写出"巨型 if-else"——每加一种新算法就要改核心逻辑，违反开闭原则。

假设你在写一个折扣计算系统。最初只有普通折扣：

```python
def calculate_price(original_price: float, discount_type: str) -> float:
    """计算折后价格——早期的简单版本"""
    if discount_type == "normal":
        return original_price * 0.9
    elif discount_type == "vip":
        return original_price * 0.8
    elif discount_type == "festival":
        return original_price * 0.7
    else:
        return original_price
```

后来业务说要加"满减""秒杀""新人首单""会员日"……每加一种，你就要在这个函数里加一个 `elif`。这个函数慢慢变成几百行的 if-else 地狱，改一个折扣可能不小心改坏另一个。而且**新加入的同事不敢删旧代码**——因为不知道哪还在用。

### 3.2 What：策略模式

**本节概念**：**策略模式**定义一组可互换的算法，把每种算法封装成独立的类，客户端运行时选择其中一种。这样加新算法就是**加新类**，而不是**改旧函数**。

### 3.3 How：Python 实现

```python
from abc import ABC, abstractmethod

# 第一步：定义"策略"接口——所有折扣都遵循这个契约
class DiscountStrategy(ABC):
    """折扣策略的抽象接口——每个具体策略都要实现 calculate"""
    @abstractmethod
    def calculate(self, price: float) -> float:
        """给定原价，返回折后价"""
        ...

# 第二步：每种折扣规则写成一个独立的类
class NormalDiscount(DiscountStrategy):
    """普通会员：9 折"""
    def calculate(self, price: float) -> float:
        return price * 0.9

class VIPDiscount(DiscountStrategy):
    """VIP 会员：8 折"""
    def calculate(self, price: float) -> float:
        return price * 0.8

class FestivalDiscount(DiscountStrategy):
    """节日促销：7 折"""
    def calculate(self, price: float) -> float:
        return price * 0.7

class NewUserDiscount(DiscountStrategy):
    """新人首单：减 50 元，但不低于 0"""
    def calculate(self, price: float) -> float:
        return max(price - 50, 0)

# 第三步：客户端代码——接受任何策略，不关心具体是哪种
class PriceCalculator:
    def __init__(self, strategy: DiscountStrategy):
         self.strategy = strategy
    
    def get_final_price(self, price: float) -> float:
        return self.strategy.calculate(price)

# 使用：想换策略就换对象，不需要改 if-else
calc = PriceCalculator(NewUserDiscount())
print(calc.get_final_price(100))  # 50（新人减 50）

calc.strategy = VIPDiscount()
print(calc.get_final_price(100))  # 80（VIP 8 折）

# 加新折扣？新建一个类就行，不动老代码！
class MemberDayDiscount(DiscountStrategy):
    """会员日：5 折"""
    def calculate(self, price: float) -> float:
        return price * 0.5
```

**改造前后对比**：

| 维度 | 改前（if-else） | 改后（策略模式） |
|------|----------------|-----------------|
| 加新折扣 | 改 `calculate_price` 函数，加 elif | 新建一个策略类 |
| 改某个折扣规则 | 在几百行 if-else 里找对应分支 | 找到对应的类，只改那一个 |
| 测试 | 所有折扣混在一起测 | 每个策略类单独测试 |
| 加折扣的人会不会改坏别人的？ | 可能 | 不会 |

### 3.4 Python 里更轻量的方式——函数就是策略

Python 里函数是一等公民，不需要为每种策略建一个类：

```python
from typing import Callable

# 策略 = 函数，不是类
def normal(price: float) -> float:
    return price * 0.9

def vip(price: float) -> float:
    return price * 0.8

# 客户端
class PriceCalculator:
    def __init__(self, strategy: Callable[[float], float]):
        self.strategy = strategy
    
    def get_final_price(self, price: float) -> float:
        return self.strategy(price)

# 使用更简洁
calc = PriceCalculator(vip)
print(calc.get_final_price(100))  # 80
```

## 4. 观察者模式——一个变了要通知很多个

### 4.1 Why：没有观察者模式时

**本节概念**：当一个对象的状态变化需要通知多个其他对象时，如果让这个对象"硬编码"地调用所有通知对象，耦合会很高——每增加一个需要通知的对象就要改源对象的代码。

```python
# 坏代码：User 类"知道"所有需要通知的东西
class User:
    def change_email(self, new_email: str):
        self.email = new_email
        # 每加一个通知，都要改这个方法
        self.send_welcome_email()
        self.update_crm_system()
        self.notify_admin()
        self.log_activity()
        # 下周 PM 说"再加个短信通知" → 又要改这里
```

**生活类比**：你订阅了一个 YouTube 频道。频道主不需要知道你是谁、你住哪，你只需要点"订阅"。他发新视频时，系统自动通知所有订阅者。如果靠频道主"记下每个粉丝的手机号然后一个个打电话"，那没法做了。

### 4.2 What：观察者模式

**本节概念**：**观察者模式（Observer）**定义了一对多的依赖关系：一个**主题（Subject）**状态变化时，自动通知所有**观察者（Observer）**。主题不需要知道观察者具体是谁，只要它们实现了同一个通知接口。

### 4.3 How：一个邮件变更通知系统

```python
from abc import ABC, abstractmethod

# —— 观察者接口 ——
class Observer(ABC):
    """所有观察者必须实现 update 方法"""
    @abstractmethod
    def update(self, user_id: str, new_email: str):
        """收到通知时做什么——每个观察者自己决定"""
        ...

# —— 具体观察者：每个做一件事 ——
class WelcomeEmailSender(Observer):
    def update(self, user_id: str, new_email: str):
        print(f"[邮件服务] 向 {new_email} 发送欢迎邮件")

class CRMUpdater(Observer):
    def update(self, user_id: str, new_email: str):
        print(f"[CRM] 更新用户 {user_id} 的邮箱为 {new_email}")

class AdminNotifier(Observer):
    def update(self, user_id: str, new_email: str):
        print(f"[管理员通知] 用户 {user_id} 变更了邮箱")

# —— 主题：用户 ——
class User:
    def __init__(self, user_id: str, email: str):
        self.user_id = user_id
        self.email = email
        self._observers: list[Observer] = []  # 观察者列表
    
    def attach(self, observer: Observer):
        """注册观察者（"订阅"）"""
        self._observers.append(observer)
    
    def detach(self, observer: Observer):
        """移除观察者（"取消订阅"）"""
        self._observers.remove(observer)
    
    def change_email(self, new_email: str):
        old_email = self.email
        self.email = new_email
        
        # 通知所有观察者——User 不关心它们各自做什么
        for observer in self._observers:
            observer.update(self.user_id, new_email)

# —— 使用 ——
user = User("user-123", "old@example.com")
user.attach(WelcomeEmailSender())
user.attach(CRMUpdater())
user.attach(AdminNotifier())

user.change_email("new@example.com")
# 输出：
# [邮件服务] 向 new@example.com 发送欢迎邮件
# [CRM] 更新用户 user-123 的邮箱为 new@example.com
# [管理员通知] 用户 user-123 变更了邮箱

# 加新通知？新建一个 Observer 子类，attach 上去就行。不改 User 类！
```

### 4.4 Python 里的简化版：用回调函数

```python
class User:
    def __init__(self, user_id: str, email: str):
        self.user_id = user_id
        self.email = email
        self._listeners: list[callable] = []  # 存回调函数
    
    def on_email_changed(self, callback):
        """注册回调"""
        self._listeners.append(callback)
    
    def change_email(self, new_email: str):
        self.email = new_email
        for callback in self._listeners:
            callback(self.user_id, new_email)

# 使用：更 Pythonic
def send_notification(user_id, new_email):
    print(f"🔔 发送通知：{user_id} → {new_email}")

user = User("user-123", "old@x.com")
user.on_email_changed(send_notification)
user.on_email_changed(lambda uid, em: print(f"📝 日志：{uid} 改了邮箱"))
user.change_email("new@x.com")
```

## 5. 工厂模式——让创建对象不再是一团乱麻

### 5.1 Why：没有工厂模式时

**本节概念**：当对象的创建逻辑复杂（需要多步骤、多判断、跨文件读配置），散落在各处的 `ClassName(...)` 调用会让系统变脆弱——换了实现类就要满世界改。

```python
# 坏代码：创建逻辑散落在各处
# 在路由 A 里：
db = PostgresConnection(host="localhost", port=5432, user="admin", password="xxx")

# 在路由 B 里：
db = PostgresConnection(host="localhost", port=5432, user="admin", password="xxx")

# 在后台任务里：
db = PostgresConnection(host="localhost", port=5432, user="admin", password="xxx")

# 有一天要换成 MySQL → 改 30 个文件
# 有一天要加连接池 → 改 30 个文件
```

### 5.2 What：工厂方法

**本节概念**：**工厂方法**把对象的创建逻辑集中到一个地方，调用方只需要说"给我一个数据库连接"，不必知道具体的类名和构造参数。

### 5.3 How

```python
from enum import Enum

class DBType(Enum):
    POSTGRES = "postgres"
    MYSQL = "mysql"
    SQLITE = "sqlite"

class DatabaseFactory:
    """创建数据库连接的工厂——所有创建逻辑在这里，只在这里"""
    
    _instances: dict = {}
    
    @classmethod
    def create(cls, db_type: DBType) -> "DatabaseConnection":
        """工厂方法：根据类型返回对应的连接"""
        if db_type == DBType.POSTGRES:
            return PostgresConnection(
                host=cls._config("DB_HOST", "localhost"),
                port=int(cls._config("DB_PORT", "5432")),
                user=cls._config("DB_USER", "admin"),
                password=cls._config("DB_PASSWORD", ""),
            )
        elif db_type == DBType.MYSQL:
            return MySQLConnection(
                host=cls._config("DB_HOST"),
                port=int(cls._config("DB_PORT", "3306")),
                user=cls._config("DB_USER"),
                password=cls._config("DB_PASSWORD"),
            )
        elif db_type == DBType.SQLITE:
            return SQLiteConnection(db_path=cls._config("SQLITE_PATH", "app.db"))
        else:
            raise ValueError(f"不支持的数据库类型: {db_type}")
    
    @staticmethod
    def _config(key: str, default: str = "") -> str:
        """从环境变量读配置，读不到用默认值"""
        import os
        return os.environ.get(key, default)

# 使用：所有地方都这样调，换数据库只改环境变量
db = DatabaseFactory.create(DBType.POSTGRES)
```

### 5.4 什么时候不需要工厂

```python
# 如果创建逻辑就这么简单：
db = PostgresConnection("localhost", 5432)

# 那不要套工厂。工厂解决的是"构建复杂、经常变"的问题，
# 不是"所有 new 都要经过工厂"。
```

## 6. 单例模式——全局只要一个实例

### 6.1 Why：什么时候需要单例

**本节概念**：**单例（Singleton）**确保一个类只有一个实例，并提供全局访问点。适用于共享资源（数据库连接池、配置对象、日志器）。

**生活类比**：一个公司只有一个 CEO。不是"每个人都可以当 CEO"，而是"CEO 这个职位只有一个实例"。你不管从哪个部门问"谁是 CEO"，答案都是同一个人。

### 6.2 Python 的方式（不需要 GoF 那种复杂做法）

```python
# 方式一：模块级变量（最 Pythonic）
# config.py
class AppConfig:
    def __init__(self):
        self.debug = True
        self.db_url = "postgresql://..."

# 模块级单例——Python import 机制保证只执行一次
config = AppConfig()

# 其他文件里：
# from config import config
# config 永远是同一个对象


# 方式二：__new__ 方法（当必须用类本身保证单例时）
class DatabasePool:
    _instance = None
    
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._initialized = False
        return cls._instance
    
    def __init__(self):
        # 注意：__init__ 每次 DatabasePool() 都会调用！
        # 用 _initialized 标志避免重复初始化
        if self._initialized:
            return
        self.connections = []
        self._initialized = True

# 测试
pool1 = DatabasePool()
pool2 = DatabasePool()
print(pool1 is pool2)  # True，同一个对象！
```

**什么时候不该用单例**：测试中很难替换、隐藏了依赖关系（函数表面看不出依赖了什么全局状态）。大多数时候用**依赖注入**（FastAPI 的 `Depends`）比单例更好。

## 7. 装饰器模式——运行时给对象加功能

### 7.1 Python `@` 装饰器 vs GoF 装饰器模式

**本节概念**：Python 的 `@decorator` 语法和 GoF 的装饰器模式**名字撞车但概念不同**。Python `@` 是在**定义时**包装函数/类（编译期）；GoF 装饰器是在**运行时**动态给对象叠加职责。

两者解决的问题类似——给已有行为加切面——但实现路径不同。Python `@` 你已经在 A1 §5 学过了，这里讲的是 GoF 的"对象装饰"。

### 7.2 场景：一杯咖啡可以加各种配料

```python
from abc import ABC, abstractmethod

# —— 基础组件接口 ——
class Coffee(ABC):
    @abstractmethod
    def cost(self) -> float:
        ...
    
    @abstractmethod
    def description(self) -> str:
        ...

# —— 具体组件：一杯基础咖啡 ——
class SimpleCoffee(Coffee):
    def cost(self) -> float:
        return 10.0
    
    def description(self) -> str:
        return "黑咖啡"

# —— 装饰器基类：持有一个被装饰的对象 ——
class CoffeeDecorator(Coffee):
    def __init__(self, coffee: Coffee):
        self._coffee = coffee  # 被装饰的对象
    
    def cost(self) -> float:
        return self._coffee.cost()
    
    def description(self) -> str:
        return self._coffee.description()

# —— 具体装饰器：加配料 ——
class Milk(CoffeeDecorator):
    def cost(self) -> float:
        return self._coffee.cost() + 3.0
    
    def description(self) -> str:
        return self._coffee.description() + " + 牛奶"

class Sugar(CoffeeDecorator):
    def cost(self) -> float:
        return self._coffee.cost() + 1.0
    
    def description(self) -> str:
        return self._coffee.description() + " + 糖"

class Ice(CoffeeDecorator):
    def cost(self) -> float:
        return self._coffee.cost() + 2.0
    
    def description(self) -> str:
        return self._coffee.description() + " + 冰"

# —— 使用：运行时自由叠加 ——
my_coffee = SimpleCoffee()
print(f"{my_coffee.description()}：¥{my_coffee.cost()}")  # 黑咖啡：¥10.0

# 加牛奶
my_coffee = Milk(my_coffee)
print(f"{my_coffee.description()}：¥{my_coffee.cost()}")  # 黑咖啡 + 牛奶：¥13.0

# 再加糖和冰
my_coffee = Sugar(Ice(my_coffee))
print(f"{my_coffee.description()}：¥{my_coffee.cost()}")  # 黑咖啡 + 牛奶 + 冰 + 糖：¥16.0
```

## 8. 适配器模式——让不兼容的接口能对接

### 8.1 Why：外部库的接口不归你管

**本节概念**：用第三方库时，它的接口（方法名、参数顺序）不一定跟你项目里的约定一致。直接使用会让你的代码被那个接口"污染"——哪天换库就要满世界改。**适配器（Adapter）**在边界做翻译。

```python
# 你的项目里有一个"发通知"的统一接口
class Notifier(ABC):
    @abstractmethod
    def send(self, to: str, title: str, body: str) -> bool:
        ...

# 现在要用飞书发通知，但飞书 SDK 的 API 是这样的：
# feishu.send_message(chat_id="xxx", content={"text": "..."})
# 参数名、结构都跟你项目的约定不一样

# 你的库还在另一个地方用企业微信，API 又不一样：
# wecom.notify(user="xxx", subject="标题", message="内容")

# 如果每个地方都直接调不同 SDK，代码会变成一锅粥
```

### 8.2 How：适配器做翻译

```python
# 飞书适配器——把"你的接口"翻译成"飞书 SDK 的调用"
class FeishuNotifier(Notifier):
    def __init__(self, feishu_client):
        self.client = feishu_client
    
    def send(self, to: str, title: str, body: str) -> bool:
        # 翻译：项目的 send(title, body) → 飞书的 send_message(chat_id, content)
        try:
            self.client.send_message(
                chat_id=to,
                content={"text": f"{title}\n{body}"}
            )
            return True
        except Exception:
            return False

# 企业微信适配器
class WeComNotifier(Notifier):
    def __init__(self, wecom_client):
        self.client = wecom_client
    
    def send(self, to: str, title: str, body: str) -> bool:
        try:
            self.client.notify(user=to, subject=title, message=body)
            return True
        except Exception:
            return False

# 使用方：只管 Notifier 接口，不管底层是谁
def alert_oncall(notifier: Notifier, message: str):
    notifier.send(to="oncall-group", title="告警", body=message)

# 换消息渠道 = 换适配器，业务代码不变
alert_oncall(FeishuNotifier(feishu_sdk))
alert_oncall(WeComNotifier(wecom_sdk))
```

## 9. 责任链模式——多个处理者依次尝试

### 9.1 Why：长长的 if-elif 处理管道

**本节概念**：当一个请求需要经过多个处理步骤，且每个步骤可以"批准/拒绝/传给下一步"时，if-elif 链会变得又长又难扩展。

```python
# 坏代码：审核管道
def review_document(doc):
    if not check_format(doc):
        return "格式错误"
    elif not check_content(doc):
        return "内容违规"
    elif not check_quota(doc):
        return "额度不足"
    # 再加一个检查 → 又是一个 elif
    return "审核通过"
```

**生活类比**：你请假要找"直属上司 → 部门经理 → HR"。每个审批者只做两件事：自己能批就批，不能批就交给下一级。你不用知道整个审批链有多大。

### 9.2 How

```python
from abc import ABC, abstractmethod

# —— 处理器抽象 ——
class Handler(ABC):
    def __init__(self):
        self._next: Handler | None = None
    
    def set_next(self, handler: "Handler") -> "Handler":
        """设置下一个处理者，返回 handler 本身以支持链式调用"""
        self._next = handler
        return handler
    
    @abstractmethod
    def handle(self, request: dict) -> str:
        """处理请求。自己处理不了就交给下一个"""
        ...

# —— 具体处理器 ——
class FormatChecker(Handler):
    def handle(self, request: dict) -> str:
        if not request.get("content"):
            return "格式错误：内容为空"
        if self._next:
            return self._next.handle(request)  # 交给下一个
        return "通过"

class ContentChecker(Handler):
    def handle(self, request: dict) -> str:
        if "违规" in request.get("content", ""):
            return "内容违规"
        if self._next:
            return self._next.handle(request)
        return "通过"

class QuotaChecker(Handler):
    def __init__(self, max_quota: int):
        super().__init__()
        self.max_quota = max_quota
    
    def handle(self, request: dict) -> str:
        if request.get("amount", 0) > self.max_quota:
            return f"额度不足：需要 {request['amount']} > {self.max_quota}"
        if self._next:
            return self._next.handle(request)
        return "通过"

# —— 组装链 ——
format_checker = FormatChecker()
content_checker = ContentChecker()
quota_checker = QuotaChecker(max_quota=10000)

# 链式组装（优雅！）
format_checker.set_next(content_checker).set_next(quota_checker)

# —— 使用 ——
req = {"content": "正常申请", "amount": 5000}
print(format_checker.handle(req))  # "通过"

req2 = {"content": "违规内容", "amount": 5000}
print(format_checker.handle(req2))  # "内容违规"

# 加新检查？新建一个 Handler 子类，插在链的任意位置
```

## 10. 状态模式——状态一变行为就变

### 10.1 Why：状态机的 if-else 噩梦

**本节概念**：一个对象在不同状态下行为完全不同时，如果所有状态逻辑都写在一个类里，会变成一个巨大的状态机 if-else。

```python
# 坏代码：订单状态——到处是 if status == "xxx"
class Order:
    def pay(self):
        if self.status == "pending":
            self.status = "paid"
        elif self.status == "paid":
            raise Exception("已支付，不能重复支付")
        elif self.status == "cancelled":
            raise Exception("已取消的订单无法支付")
    
    def cancel(self):
        if self.status == "pending":
            self.status = "cancelled"
        elif self.status == "paid":
            self.status = "refunding"
        elif self.status == "refunding":
            raise Exception("已在退款中")
```

### 10.2 How：每种状态一个类

```python
from abc import ABC, abstractmethod

# —— 状态接口 ——
class OrderState(ABC):
    @abstractmethod
    def pay(self, order: "Order") -> None:
        ...
    
    @abstractmethod
    def cancel(self, order: "Order") -> None:
        ...

# —— 具体状态 ——
class PendingState(OrderState):
    def pay(self, order):
        print("支付成功")
        order.state = PaidState()
    
    def cancel(self, order):
        print("订单已取消")
        order.state = CancelledState()

class PaidState(OrderState):
    def pay(self, order):
        raise Exception("已支付，不能重复支付")
    
    def cancel(self, order):
        print("已支付订单——进入退款流程")
        order.state = RefundingState()

class CancelledState(OrderState):
    def pay(self, order):
        raise Exception("已取消的订单无法支付")
    
    def cancel(self, order):
        raise Exception("已取消，无需再次取消")

class RefundingState(OrderState):
    def pay(self, order):
        raise Exception("退款中，无法支付")
    
    def cancel(self, order):
        raise Exception("已在退款中")

# —— 订单类 ——
class Order:
    def __init__(self):
        self.state: OrderState = PendingState()  # 初始状态
    
    def pay(self):
        self.state.pay(self)      # 委托给当前状态对象
    
    def cancel(self):
        self.state.cancel(self)

# —— 使用 ——
order = Order()
order.pay()     # 支付成功
order.cancel()  # 已支付订单——进入退款流程
```

## 11. 企业应用与 DDD 常见模式

**本节概念**：以下模式来自企业应用架构和 DDD（领域驱动设计），不在 GoF 23 里，但在后端开发中更常用。

| 模式 | 解决的痛 | 一句话 |
|------|----------|--------|
| **Repository（仓储）** | 业务逻辑里到处是 SQL/ORM 细节 | 把"查数据"抽象成领域层的接口，实现藏在基础设施层 |
| **Aggregate（聚合）** | 一致性边界不清，到处改同一张表 | 一个事务只改一个聚合根；跨聚合用最终一致 |
| **Domain Event（领域事件）** | "做完 A 还要通知 B/C"写满 if | 在领域代码里发事件，handler 订阅；与消息队列对接 |
| **Anti-Corruption Layer（防腐层）** | 外部系统模型又丑又稳变，污染核心代码 | 边界处翻译——外部 DTO ↔ 领域对象，厚一点没关系 |
| **Value Object（值对象）** | 把"标识"和"可替换的值"混写 | 没独立 ID 的东西（金额、地址、时间段）做成不可变值对象 |
| **Application Service** | 用例编排无处可放 | 薄层：管事务边界、鉴权、调领域——不放业务规则 |

## 15. 与 AI Agent 代码的关系

**本节概念**：Agent 框架（LangChain、自研 Agent）里大量使用策略、责任链、观察者等模式。理解模式能帮你读懂框架源码。

| 模式 | Agent 中的典型应用 |
|------|-------------------|
| **策略** | 不同 LLM 提供商（OpenAI/Anthropic/Ollama）切换；不同检索策略（向量/关键词/混合） |
| **责任链** | Prompt 处理管道（模板填充 → 长度校验 → 注入上下文 → 调用 LLM） |
| **观察者** | 流式输出回调（每收到一个 token 就通知 UI 更新） |
| **适配器** | MCP 工具适配（外部工具的接口 → Agent 内部统一 Tool 接口） |
| **状态** | Agent 的 ReAct 循环（思考中 → 调工具 → 等工具结果 → 生成回答） |
| **工厂** | 根据配置创建不同类型的 Agent（聊天 Agent / RAG Agent / 多工具 Agent） |

**实际例子——Agent 工具调用的策略模式**：

```python
from abc import ABC, abstractmethod

# 统一工具接口（适配器模式）
class AgentTool(ABC):
    @abstractmethod
    def name(self) -> str: ...
    
    @abstractmethod
    def description(self) -> str: ...
    
    @abstractmethod
    def run(self, input_str: str) -> str: ...

# 不同工具 = 不同策略
class SearchTool(AgentTool):
    def name(self): return "search"
    def description(self): return "搜索互联网获取信息"
    def run(self, query: str) -> str:
        return f"搜索结果：关于'{query}'的信息..."

class CalculatorTool(AgentTool):
    def name(self): return "calculator"  
    def description(self): return "进行数学计算"
    def run(self, expression: str) -> str:
        return str(eval(expression))

# Agent 持有工具列表 = 策略模式 + 适配器模式
class SimpleAgent:
    def __init__(self, tools: list[AgentTool]):
        self.tools = {t.name(): t for t in tools}  # 策略字典，不是 if-else！
    
    def execute_tool(self, tool_name: str, input_str: str) -> str:
        tool = self.tools.get(tool_name)
        if not tool:
            return f"未知工具：{tool_name}"
        return tool.run(input_str)
```

## 16. 反模式与过度设计

**本节概念**：知道"不该做什么"和知道"该做什么"同样重要。

| 反模式 | 症状 | 解药 |
|--------|------|------|
| **万能 Service** | 几千行的 `XxxManager` 处理一切 | 按职责拆 Service，一个 Service 做一件事 |
| **过早泛化** | 只有两个实现就上了"抽象工厂 + 插件体系" | 三次原则：同样模式出现三次才抽象 |
| **Service Locator 滥用** | 全局 `getBean()`，依赖看不清 | 用依赖注入（FastAPI Depends），让依赖显式化 |
| **分布式单体** | 很多微服务却共享数据库、一起发布 | 回到 B6 §3，用有界上下文检查边界 |
| **过度设计** | 一个 50 行的脚本里有 5 个设计模式 | 模式是代价——多一层抽象多一层理解成本 |

## 18. 常见误区

1. **"项目里类名带 Factory 就是工厂模式"**——不一定，可能只是命名，要看是否隔离了构造细节。
2. **"模式用得越多越好"**——模式是代价：多一层抽象就多一层阅读成本。通常三次重复再抽象。
3. **"Python `@decorator` = GoF 装饰器模式"**——同名但概念不同。Python `@` 是定义时包装，GoF 是运行时叠加。
4. **"单例很简单，哪里都能用"**——单例 = 全局可变状态，测试和并发时是灾难。大多数时候依赖注入更好。
5. **"设计模式是 Java 的东西，Python 不需要"**——思想通用，但 Python 里很多模式被语言特性（函数一等公民、装饰器、迭代器协议）内建了。

## 19. 面试怎么答

**标准句式**：「我们遇到的问题是 ___，所以用了 ___，代价是 ___，如果重来会 ___。」

**好的回答**：
"我们 Agent 平台有 5 种检索策略（向量检索、关键词检索、混合检索、时间衰减检索、人工规则优先检索）。最开始写在一个 300 行的 `if strategy == 'xxx'` 里，加一种新策略要改核心逻辑。后来用策略模式拆成 5 个类，加新策略就是新建一个类。代价是多了一层抽象，但换来了可测试性——每种策略可以独立跑单测。"

**不好的回答**：
"单例模式是确保一个类只有一个实例。"（只会背定义，没说场景和代价）
